## 1 目标与范围

### 1.1 目标

在 2 周内完成 Weave v0.2.0 的 Phase 0 开发基线，使 Weave 能够：

1. 在 DSH `0.1.1-rc.2+` 环境中正常运行，并验证 `ctx.subagents` 原生子代理 API 可用；
2. 通过 `ExecutorRegistry` 统一发现 DSH 子代理 / Codex / Claude Code / ACP 四类执行器；
3. 通过 `DelegationService` 基于 `ctx.subagents.start` 完成统一委托执行，不再自研进程管理；
4. 支持任务状态机、保温期反馈路由、修订上下文注入；
5. 打通知识导入主链路：Web 上传 → AnyDoc 转换（`@firecrawl/anydoc` 唯一选型）→ candidate 预览/确认 → 候选审核 → 知识注入 prompt；
6. 提供 CLI/MCP 基础能力，支撑日常手工验证与自动化验收；
7. 建立完整测试与验收闭环，满足 FDD 7.1 全部 17 项 P0 验收（含架构文档第 15.1 节全部 14 项）。

### 1.2 范围

**Phase 0 包含：**

- DSH 插件环境验证、`ctx.subagents` API 验证；
- 仓库/插件工程脚手架（P0-BOOTSTRAP）与执行器 Bundle 安装/启用（P0-EXEC-021）；
- `ExecutorRegistry` 发现与分类；
- `team.yaml` 加载与执行器校验；
- SQLite + 单写者队列持久化基础；
- 任务状态机与反馈路由；
- `SessionTracker` 修订上下文；
- `DelegationService` 重写；
- 知识目录/元数据模型、AnyDoc 转换管线、知识导入 UI、候选知识审核；
- `KnowledgeEngine` 检索与注入；
- CLI/MCP 基础工具；
- 安全熔断、进程限流、循环检测；
- 审计日志、崩溃恢复、DAG 面板、Dashboard 框架；
- Phase 0 全链路验收测试。

**Phase 0 不包含：**

- Graphify 知识图谱（P1）；
- Obsidian 双向同步（P1）；
- 浏览器链接采集与浏览器插件（暂缓）；
- 自定义 CLI 执行器主路径（非 P0 后备方案）；
- P1 的置信度模型调优、知识保鲜后台巡检、双向反思完整闭环。

## 2.1 仓库/插件工程形态

| 项 | 定义 |
| --- | --- |
| 交付形态 | 单一 npm 包 `@deepseek-ai/dsh-plugin-weave`，与 DSH 插件实际交付形态一致（参照 `node_modules/@deepseek-ai/dsh-*` 包结构 + cordis 配置挂载） |
| 仓库布局 | 仓库根即包根：`package.json`（main/exports 指向 `src/plugins/weave/index.ts`）、`tsconfig.json`（strict）、`vitest.config.ts`、`eslint.config.js`；源码 `src/plugins/weave/`（index.ts 为插件入口，功能模块分子目录）；测试 `src/plugins/weave/__tests__/`，公共夹具（如 `MockSubagentsContext`）位于 `src/plugins/weave/__tests__/helpers/` |
| 运行态边界 | 插件代码以 cordis 服务形式挂载到 DSH 上下文（`ctx.weave`）；业务数据仍在 `~/.dsh/` 下（架构 9.1），仓库只含代码、测试与构建产物 |
| 工具链 | TypeScript（strict）+ Vitest（单测 node 环境；组件测试 jsdom + @testing-library/react）+ ESLint + pnpm；`pnpm typecheck && pnpm lint` 为静态检查入口 |
| 加载冒烟 | `plugin-loading.test.ts` 通过 cordis 加载最小插件（注册 weave 服务与一个示例 context 扩展），断言插件可被 DSH 加载、服务可被注入——作为所有 `testCommand` 的运行前提 |

> 依据：审核报告 E7 —— DSH 插件实际交付形态为 npm 包 + cordis 配置，而非仓库内独立 `src/plugins/weave` 目录；本表据此收敛工程形态并保留统一测试路径。

## 4 依赖说明

### 4.1 关键路径

Phase 0 存在两条关键路径，最终汇聚到 P0-TEST-019：

```text
全局前置（所有 testCommand 的运行前提）
P0-BOOTSTRAP → 全部任务

关键路径 A（执行器/任务链路）
P0-ENV-001 → P0-EXEC-021（执行器 Bundle 安装与启用）
  → P0-REG-002 + P0-DB-004
  → P0-STATE-005
  → P0-SAFETY-015
  → P0-DELEG-007
  → P0-CLI-014 / P0-KINJECT-013

关键路径 B（知识导入/知识注入链路）
P0-DB-004 → P0-KBLD-009
  → P0-ANYDOC-010
  → P0-KUI-011
  → P0-KREVIEW-012
  → P0-DASH-020 / P0-KINJECT-013

汇聚点
P0-KINJECT-013 依赖 P0-DELEG-007 与 P0-KREVIEW-012（HI-5：审核转正 P0），将执行器链路与知识链路合并，且注入数据源为审核后的 active 知识；P0-EXEC-021 的兼容性结论决定 AC-EXEC-001 / 架构 15.1#2 的验收口径；
P0-TEST-019 最终验收所有 Phase 0 任务。
```

### 4.2 并行轨道

| 轨道 | 任务 | 说明 |
| --- | --- | --- |
| 0：脚手架 | P0-BOOTSTRAP | 全局前置；仓库/插件工程脚手架与测试工具链就绪后，其余任务才能运行 `testCommand` |
| A：环境/基础设施 | P0-ENV-001、P0-EXEC-021、P0-DB-004 | 最先启动；P0-ENV-001 决定后续所有 `ctx.subagents` 相关任务是否可行；P0-EXEC-021 在 spike 后立即执行 Bundle 安装与兼容性验证 |
| B：执行器/任务调度 | P0-REG-002、P0-TEAM-003、P0-STATE-005、P0-SESSION-006、P0-SAFETY-015、P0-DELEG-007、P0-FEEDBACK-008、P0-CLI-014 | 与知识轨道尽量并行，但在 P0-DELEG-007 完成前不要做 CLI 联调；P0-REG-002 的真实 provider 分类验证依赖 P0-EXEC-021 |
| C：知识 | P0-KBLD-009、P0-ANYDOC-010、P0-KUI-011、P0-KREVIEW-012、P0-KINJECT-013 | 与轨道 B 并行；与 B 的汇合点是知识注入 |
| D：可观测/UI/恢复 | P0-AUDIT-016、P0-DAG-017、P0-DASH-020、P0-RECOVERY-018 | 可在轨道 B/C 关键模块稳定后并行开发 |
| E：验收 | P0-TEST-019 | 全部完成后执行，作为 Phase 0 收口 |

### 4.3 依赖设计原则

1. **避免环形依赖**：执行器调用、知识转换、状态机均不存在循环依赖。
2. **先验证后实现**：所有依赖 `ctx.subagents` 的任务必须先等 P0-ENV-001 确认 DSH API 可用。
3. **最小可用优先**：P0-DELEG-007 先打通 `spawn/fork` 与 Codex/Claude/ACP 最少分支，再扩展错误映射与取消语义。
4. **知识注入不阻塞主链路**：P0-KINJECT-013 可先用 active 知识的简单检索版本完成，P1 再优化 BM25/jieba。
5. **测试任务收敛**：P0-TEST-019 不并行开发静态验收清单，而是在各任务完成时增量补充验收用例，最后统一跑全量。

## 5 测试策略

### 5.1 总体原则

- 所有任务以 P0-BOOTSTRAP 脚手架为运行前提；P0-EXEC-021 在 P0-ENV-001 spike 后启动，其兼容性结论决定 AC-EXEC-001 / 架构 15.1#2 的验收口径（不兼容则按方案B 降级，见 §8 DoD）。
- 每个任务都配有独立可执行的 `testCommand`，必须能在无真实 Codex/Claude Code 的外部环境下通过 mock 运行。
- 测试优先验证 P0 架构约束：不自研 spawn/kill、不绕过 `ctx.subagents`、不提前写 active 知识。
- 对真实外部执行器采用“spike 通过 + CI mock 常驻”的策略：P0-ENV-001 用真实 DSH 环境做冒烟，CI 使用 `MockSubagentsContext` 保证稳定。
- 每个模块先跑单测，再跑跨模块集成测试，最后跑全量验收，避免一次改多个模块后无法定位。

### 5.2 测试分层

| 层级 | 内容 | 工具 | 命令 |
| --- | --- | --- | --- |
| 静态检查 | TypeScript 类型、lint | tsc、eslint | `pnpm typecheck && pnpm lint` |
| 单元测试 | 纯逻辑模块：状态机、注册表、SessionTracker、限流、转换管线 | Vitest | `pnpm vitest run <file>` |
| 组件测试 | 知识导入 UI、DAG 面板、Dashboard | Vitest + Testing Library | `pnpm vitest run <component>.test.tsx` |
| 集成测试 | DelegationService + 安全 + 状态机 + 知识注入；AnyDoc 管线 + 审核 | Vitest | `pnpm vitest run <integration>.test.ts` |
| E2E 验收 | DSH 会话内 `/weave` 命令、Web 导入全链路 | Playwright（可选） | `pnpm test:e2e` |
| 最终回归 | 全部 P0 验收项 | Vitest | `pnpm test -- --runInBand` |

### 5.3 Mock 与测试夹具

- `MockSubagentsContext`：实现 `list()` 返回 `['spawn','fork','codex','claude-code','zcode']`；实现 `start(executorId, request)`，支持 `signal` abort 模拟。（注：`zcode` 为 mock 占位名，真实 ACP provider 名为 `acp`，分类规则一致；真实环境 `list()` 见 P0-EXEC-021 结论。）
- `MockProcessLimiter`：可控并发槽位与小时频率，用于验证“超限排队不熔断”。
- `MockAnyDoc`：用 fixture 文件（`docx`/`pdf`/`csv` 等）输出确定 GFM，避免 CI 依赖外部转换服务。
- 临时 SQLite：使用 `:memory:` 或每测试独立临时目录，保证测试隔离。
- Golden 文件：为 AnyDoc 输出保存 golden Markdown，防止转换结果漂移。

## 8 完成定义（DoD）

Phase 0 完成的判断标准：

1. FDD 7.1 全部 17 项 P0 验收测试通过（FDD 7.1 为架构 15.1 全部 14 项的超集；其中 15.1#2 按本规划 §2 方案A/B 口径执行）。
2. 仓库/插件工程脚手架（P0-BOOTSTRAP）就绪：`package.json`/`tsconfig.json`/`vitest.config.ts`/eslint 配置齐备，示例插件最小加载冒烟通过，全部 `testCommand` 可运行。
3. 执行器 Bundle（`dsh-subagent-codex` / `dsh-subagent-claude-code` / `dsh-subagent-acp`）已安装并启用，`ctx.subagents.list()` 出现对应 provider；若实证与 DSH `0.1.1-rc.2` 不兼容，按方案B 口径降级（spawn/fork 必过，其余安装后验证）并在文档记录结论。
4. `ExecutorRegistry` 发现的执行器只通过 `ctx.subagents.start` 调用；代码中不存在 Weave 自研进程管理路径。
5. `DelegationService.buildPrompt` 在修订场景下包含“上一版输出 + 用户反馈历史”；P0 委托 prompt 不引用 P1 CLI 命令（如 `/weave knowledge search`）。
6. 知识导入流程满足：上传 → 转换 → 预览 → 确认 → candidate → 审核 → active；未确认前 `knowledge/_agent` 不出现 active 内容。
7. AnyDoc 选型唯一为 `@firecrawl/anydoc` 且经 P0-ENV-001 / P0-EXEC-021 验证可安装；转换失败不污染知识目录；Graphify 未进入 Phase 0。
8. `pnpm typecheck && pnpm lint && pnpm test -- --runInBand` 全绿。
9. 最终文档矩阵（FDD/SDD/TDD/架构）与实现一致，必要时更新 ADR。
