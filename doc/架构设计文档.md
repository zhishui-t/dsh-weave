第一部分：系统概述

1.1 项目定位

织（Weave） 是一套构建在 DSH（DeepSeek Harness） 之上的多 Agent 团队协作与知识成长框架。

它把 Agent、知识、记忆、工具、经验编织在一起，让团队可以协作、可以成长、可以沉淀。

```
│  ③ 成长系统：双向反思、置信度、自动转正               │

│  ⑤ 持续交互：保温期、反馈路由、修订上下文注入        │
```

1.3 设计原则

原则 说明
DSH 原生 Weave 是 DSH 插件，复用 ctx.subagents
统一子代理 执行器通过 DSH subagent 系统统一调用
核心无 LLM P0 调度规则驱动
一切皆配置 团队、角色、执行器全 YAML 定义
文件优先 知识为 Markdown + frontmatter
渐进成长 知识先 candidate 后 active
人工优先 人工修订单向 supersede
知识会老 freshness_score 衰减
任务可迭代 保温期 + 修订上下文注入
无侵入 执行器无需感知 Weave
资源由 DSH 管 进程生命周期交给 DSH，Weave 只跟踪状态

1.4 关键设计约束

· 角色完全自定义
· Weave 核心无 LLM
· 执行器四类：DSH 子代理 / Codex / Claude Code / 其它 ACP 协议工具
· 进程管理委托 DSH：Weave 不自行 spawn/kill 进程
· 单活动版本约束
· 单机单进程约束
· 非交互模式限制：子代理执行中需用户批准的操作自动拒绝
· ephemeral 线程限制：DSH 子代理每次创建临时线程，无跨任务记忆

2.2 执行器四类模型

2.2.1 四类执行器

类别 注册方式 调用方式 进程管理 会话保持
DSH 子代理 DSH 内置 spawn/fork 或自定义 provider ctx.subagents.start('spawn'/'fork'/'...') DSH 内部 ephemeral 线程

Claude Code @deepseek-ai/dsh-subagent-claude-code ctx.subagents.start('claude-code', request) DSH 内部 一次性/由 provider 决定
其它 ACP 工具 @deepseek-ai/dsh-subagent-acp ctx.subagents.start('zcode'/'...', request) DSH 内部 ACP 进程内驱动

2.2.2 关键约束：ephemeral 线程

dsh-subagent-codex 每次调用创建临时线程（ephemeral: true），任务完成后线程销毁。这导致：

· DSH 子代理不自带跨任务会话保持
· Weave 的"保温期"修订不能依赖子代理自身记忆
· Weave 必须在每次委托 prompt 中注入完整上下文（上一版输出 + 用户反馈）

第三部分：执行器模型设计

3.1 ExecutorRegistry

3.1.1 职责

· 通过 ctx.subagents.list() 发现 DSH 已注册的全部 subagent provider
· 自动分类为 DSH 子代理 / Codex / Claude Code / ACP
· 统一提供执行器查询接口

3.1.2 类设计

```typescript
import type { SubagentCapabilities } from '@deepseek-ai/dsh-subagent'

type ExecutorKind =
  | 'dsh_subagent'
  | 'codex'
  | 'claude_code'
  | 'acp'

interface ExecutorInfo {
  id: string
  name: string
  kind: ExecutorKind
  /** 真实 DSH 0.1.1-rc.2 SubagentCapabilities（start-time 特性），由 provider 注册时声明 */
  capabilities: SubagentCapabilities
}

class ExecutorRegistry {
  private executors: Map<string, ExecutorInfo> = new Map()

  load(ctx: Context): void {
    // ctx.subagents.list() 为同步方法，返回已注册 provider 名
    const providers = ctx.subagents.list()
    for (const provider of providers) {
      const kind: ExecutorKind =
        provider === 'codex'          ? 'codex'
        : provider === 'claude-code'  ? 'claude_code'
        : provider === 'spawn' || provider === 'fork' ? 'dsh_subagent'
        : /* 其它通过 ACP 注册的外部工具 */ 'acp'

      const providerInfo = ctx.subagents.getProvider(provider)
      this.executors.set(provider, {
        id: provider,
        name: provider,
        kind,
        capabilities: providerInfo?.capabilities
          ?? { outputSchema: false, depthLimit: false, toolFilter: false, persona: false },
      })
    }
  }

  get(id: string): ExecutorInfo | undefined
  list(): ExecutorInfo[]
  kindOf(id: string): ExecutorKind | undefined
}
```

> 说明（第 2 轮修订）：
> - `SubagentCapabilities` 为 `{ outputSchema, depthLimit, toolFilter, persona }`（真实 DSH API 的 start-time 特性声明），通过 `ctx.subagents.getProvider(name).capabilities` 读取；原 `supports_feedback_loop / non_interactive / ephemeral_session` 在 DSH API 中无数据源，且原实现为全同常量，已删除。
> - 非交互、会话保持等运行期特性不由 provider 声明；P0 无 capabilities 消费方，该字段仅作展示/预留。

3.2 非 P0 扩展：自定义 CLI 执行器（可选）

> P0 主路径只含 DSH 子代理 / Codex / Claude Code / ACP 四类。自定义 CLI 仅作为没有 ACP 时的后备方案，统一由 Weave 通过 DSH subprocess/shell 执行，或包装成自定义 SubagentProvider。

```yaml
# ~/.dsh/executors.yaml（非 P0 可选）
schema_version: "1"

executors:
  - id: my-agent
    name: 自研 Agent
    command: myagent
    args_template: "run {prompt}"
    cwd_parameter: --cwd {cwd}
    timeout_parameter: --timeout {sec}
    session_parameter: --session {session_id}    # 可选，有则支持保温期
    output_mode: stdout
    cancel_signal: SIGTERM
    non_interactive: true
    env_tokens: [MY_AGENT_API_KEY]
    process_limits:
      max_concurrent: 1
      max_per_hour: 10
```

3.3 角色绑定

```yaml
# team.yaml
roles:
  - id: designer
    executor: codex              # Codex provider
    stages: [prepare, design]    # HI-4：该角色执行的 DAG 阶段名
  - id: coder
    executor: zcode              # 其它 ACP 工具（或自定义 DSH provider）
    stages: [implement, test, integrate, execute, deploy]
```

绑定规则（HI-4）：DAG 构建时每个阶段按 `roles` 声明顺序取第一个声明该阶段的角色；未命中时按“阶段名 = 角色 id”兜底；仍无 → `configuration_error`（不静默跳过）。matcher 未命中难度 → `default_difficulty`（缺省 `hard`）。

4.1.2 配置校验

# 校验项 失败行为
1 schema_version = "1" 加载失败
2 角色 id 唯一 校验失败
3 executor 已注册（DSH 子代理 / Codex / Claude Code / ACP provider） 校验失败
4 非 P0 自定义 CLI 命令存在于 PATH 校验失败
5 max_concurrent_tasks > 0 校验失败
6 每角色 stages 非空；每模板阶段至少绑定一个角色；default_difficulty 模板存在 校验失败（HI-4）
7 executor_limits 的 max_concurrent/max_per_hour > 0 校验失败（ME-6）

4.2 Orchestrator

4.2.1 任务分解（规则驱动）

使用 task_decomposition.matchers 匹配难度（未命中用 `default_difficulty` 兜底），dag_templates 生成 DAG；每个阶段按角色 `stages` 绑定角色（规则见 3.3，HI-4），绑定失败 → DAG 构建失败（configuration_error）。

4.2.2 任务状态机（14 态 + 32 条转移）

```
| # | 当前 → 目标 | 触发 | 说明 |
| --- | --- | --- | --- |
| 1 | WAITING → BLOCKED | 依赖检查：上游未全部到成功终态 | 上游完成/失败时由传播规则（2.2.4）重估 |
| 2 | BLOCKED → WAITING | 依赖全部满足（或上游被 override） | 进入就绪队列 |
| 3 | WAITING → RUNNING | runReadyTasks 派发（角色软限制 + 执行器槽位） | 角色已绑定（见 2.2.7） |
| 4 | RUNNING → COMPLETED | stopReason=completed | 写 result；随后自动进入 AWAITING_FEEDBACK（#10） |
| 5 | RUNNING → FAILED | 按错误映射（error/max-tokens/refusal/基础设施 reject/timeout/可选 permission_denied） | 写 error_type；计熔断 |
| 6 | RUNNING → BANNED | 断路器触发（连续失败 ≥ 3） | 计熔断；后续 #20/#21 |
| 7 | RUNNING → LOOP_TERMINATED | 循环检测命中 | 计熔断（循环防护） |
| 8 | RUNNING → INTERRUPTED | 外部中断（非用户取消） | 可恢复（#26）或取消 |
| 9 | RUNNING → CANCELLED | 用户取消 | 不计熔断；stopReason=aborted |
| 10 | COMPLETED → AWAITING_FEEDBACK | 自动进入保温期 | feedback_expires_at = now + 1800s |
| 11 | AWAITING_FEEDBACK → REVISION_RUNNING | 用户 revise | revision_count+1；recordRevision；保温期重置 |
| 12 | AWAITING_FEEDBACK → CLOSED | accept 或保温期超时 | clearRevision；写 closed_at |
| 13 | AWAITING_FEEDBACK → CANCELLED | 用户 cancel | 终态，参与失败传播 |
| 14 | REVISION_RUNNING → COMPLETED | 修订委托完成 | 写 result；保温期重置 |
| 15 | REVISION_RUNNING → FAILED | 修订失败/超时（ME-5） | previous_result 保留；revision_count 不回退；可 #18 retry |
| 16 | REVISION_RUNNING → CANCELLED | 修订取消（ME-5） | 不计熔断；上下文保留 |
| 17 | CLOSED → AWAITING_FEEDBACK | reopen（24h 窗口内） | reopen_count+1；保温期重置 |
| 18 | FAILED → WAITING | retry | 失败计数保留（断路器侧） |
| 19 | FAILED → SKIPPED | skip | skip_override=1 |
| 20 | BANNED → COOLDOWN | 冷却开始（expiry/手动解除） | 记录 cooldown_seconds |
| 21 | BANNED → SKIPPED | skip（熔断下） | skip_override=1 |
| 22 | COOLDOWN → WAITING | 冷却结束 | 可再次派发 |
| 23 | COOLDOWN → SKIPPED | 冷却期间 skip | skip_override=1 |
| 24 | LOOP_TERMINATED → WAITING | retry | — |
| 25 | LOOP_TERMINATED → SKIPPED | skip | — |
| 26 | INTERRUPTED → WAITING | retry | — |
| 27 | INTERRUPTED → SKIPPED | skip | — |
| 28 | INTERRUPTED → CANCELLED | cancel | 终态 |
| 29 | CANCELLED → WAITING | retry | 终态恢复（用户显式） |
| 30 | CANCELLED → SKIPPED | skip | — |
| 31 | WAITING → CANCELLED | cancel（等待中） | — |
| 32 | BLOCKED → CANCELLED | cancel（阻塞中） | — |
```

5.1 核心原则

5.2 DelegationService

```typescript
class DelegationService {
  constructor(
    private ctx: Context,
    private executorRegistry: ExecutorRegistry,
    private sessionTracker: SessionTracker,
    private processLimiter: ProcessLimiter,
    private knowledgeEngine: KnowledgeEngine,
  ) {}

  async executeTask(
    task: TaskRecord,
    role: RoleConfig,
    context: TaskContext,
    cancelSignal: AbortSignal,
  ): Promise<SubagentTaskOutput> {
    const executorInfo = this.executorRegistry.get(role.executor)
    if (!executorInfo) throw new WeaveError('executor_unavailable')

    if (!this.processLimiter.acquire(role.executor)) {
      await this.waitForProcessSlot(role.executor, cancelSignal)
    }

    try {
      const knowledge = await this.knowledgeEngine.searchForInjection(...)
      const revisionContext = await this.sessionTracker.getRevisionContext(task.id)
      const prompt = this.buildPrompt(task, role, context, knowledge, revisionContext)

      // DSH 契约（0.1.1-rc.2）：prompt 为 ContentBlock[]，parent/signal 必填；
      // cwd 由 DSH 从 parent session 的工作目录解析，不需要 Weave 显式传入
      const startedAt = Date.now()
      const run = await this.ctx.subagents.start(role.executor, {
        prompt: [{ type: 'text', text: prompt }],
        parent: context.parentAgent,
        signal: cancelSignal,
      })

      // 子代理失败时 run.result resolve（stopReason='error'），不 reject；仅基础设施故障 reject
      const result = await run.result
      const durationMs = Date.now() - startedAt

      return this.mapResult(run, result, durationMs)
    } finally {
      this.processLimiter.release(role.executor)
    }
  }
}
```

`mapResult` 将 `SubagentRun`（`{ id, localAgent?, result, dispose() }`）与 `SubagentResult`（`{ output: ContentBlock[], structured?, diagnostic?, stopReason }`）映射为 Weave 内部结果 `SubagentTaskOutput`（见 5.5 与 SDD 2.3.5）：

- `id` ← `run.id`；`output` ← `result.output`（ContentBlock[]，非 stdout 文本）；`diagnostic` / `structured` 原样透传；
- `stopReason` 原样保留（`completed / aborted / error / max-tokens / refusal` → 任务终态见 5.5）；
- `duration_ms` 由 Weave 自计时（start() → run.result 完成），DSH API 不提供；
- 取消/放弃已发布的运行：调用 `run.dispose()`（幂等），DSH 侧终止为 `aborted`。

5.5 错误映射（第 2 轮修订：按真实 DSH 0.1.1-rc.2）

DSH 的 `SubagentResult.stopReason` 枚举只有：`completed` / `aborted` / `error` / `max-tokens` / `refusal`（merge-extensible，后端可加变体；消费方对已知分支处理、default 兜底）。原 `timeout / execution_failed / permission_denied / parse_failed / crash / unavailable` 不是 DSH 枚举，映射规则重写如下：

| 来源 | 值 | 任务终态 | 计入熔断 | 说明 |
| --- | --- | --- | --- | --- |
| DSH `stopReason` | `completed` | COMPLETED | 否 | 子代理正常完成；非交互拒绝可能以此出现（见 5.6） |
| DSH `stopReason` | `aborted` | CANCELLED | 否 | 请求信号取消 / `run.dispose()`，与用户取消一致 |
| DSH `stopReason` | `error` | FAILED | 是 | 模型或传输失败（子代理失败时 `run.result` resolve，不 reject） |
| DSH `stopReason` | `max-tokens` | FAILED | 是 | 子代理到达 token 上限 |
| DSH `stopReason` | `refusal` | FAILED | 是 | 子代理拒绝任务 |
| `ctx.subagents.start()` 拒绝 / `run.result` 因基础设施故障 reject | 基础设施故障 | FAILED | 是 | DSH 无法用 stopReason 表示的故障 |
| Weave 应用层 | `timeout` | FAILED | 是 | Weave 委托计时器超时（触发 cancelSignal / dispose；stopReason 通常表现为 aborted，任务终态以 Weave 判定为准） |
| Weave 应用层 | `permission_denied` | FAILED | 是 | 可选启发式识别（见 5.6），非 DSH 枚举 |
| Weave 应用层 | `executor_unavailable` | 委托前拦截 | 否 | 注册表校验失败或 provider 不存在，不进入执行；不计熔断 |

`tasks.error_type` 存储以上"值"列（DSH stopReason 或 Weave 应用层枚举），供审计与断路器参考。

5.6 非交互模式限制（第 2 轮修订）

DSH 子代理在非交互模式下，需用户批准的操作会被子代理内层拒绝，但 **DSH `stopReason` 没有 `permission_denied` 枚举**：拒绝发生在子代理内层，最终表现为子代理输出/诊断文本说明（可能以 `completed` 结束并说明无法执行，或以 `error` 结束）。

- **Weave P0 不强制识别该情况**：任务按 `stopReason` 正常映射（5.5）；
- **可选启发式识别（尽力而为，不作为 P0 验收强制项）**：对 `result.output` 文本与 `result.diagnostic` 匹配拒绝模式（如"需要批准 / 需要授权 / approval required / authorization required / permission denied / 操作被拒绝"），命中则将任务终态定为 FAILED 并写入 `error_type='permission_denied'`（仅作审计辅助标记，不是 DSH API 枚举）；未命中则按 stopReason 映射。

ADR-030 摘要

背景：v0.1.0-rc 自研 SubagentAdapter + 进程管理，但 DSH 已原生提供 ctx.subagents。

决策：Weave 通过 ctx.subagents.start 调用执行器，不再自行管理进程。

后果：DelegationService 大幅简化；进程生命周期由 DSH 保证。

ADR-031 摘要

背景：dsh-subagent-codex 每次创建 ephemeral 线程，任务完成后销毁。

决策：Weave 在 SessionTracker 记录上一版输出和用户反馈，修订时注入新 prompt。

后果：修订 prompt 更长，需控制长度。


ADR-033 摘要

背景：v0.2.0 初稿把执行器分为“DSH 子代理插件”和“外部 CLI”，但 DSH 0.1.1-rc.2 的 `ctx.subagents` 并不直接支持任意 command 字符串。

决策：执行器收敛为四类：DSH 子代理（spawn/fork/自定义 provider）、Codex、Claude Code、其它 ACP 协议工具；统一通过 `ctx.subagents.start(executorId, request)` 调用。自定义 CLI 仅作为非 P0 后备方案。

后果：ExecutorRegistry 只需基于 `ctx.subagents.list()` 分类；DelegationService 无需区分 source/command 分支；外部工具若支持 ACP 即可低成本接入。

C. 知识导入与角色学习决策摘要（2026-08-24 讨论收敛）

## C.1 知识导入以界面操作为主

- P0 入口：Web 界面“导入知识”，支持文件上传/拖拽；
- 文件类型：DOC/DOCX/PDF/PPT/Excel/EPUB/CSV/RTF/ODT；
- 通过 AnyDoc（`@firecrawl/anydoc`，唯一选型，见 FDD 4.2.1）统一转换为 GitHub-Flavored Markdown；
- 转换后生成 candidate 知识，用户预览/编辑/确认后进入审核流程；
- CLI/MCP 仅作为自动化补充。

## C.2 角色学习流程

1. 在 team.yaml 定义角色；
2. 通过界面导入项目文档/技能文档，选择归属（角色/项目/版本/知识层级）；
3. AnyDoc 将文档转为 Markdown；
4. 生成 candidate 知识卡片；
5. 审核转正 candidate → active；
6. 角色执行任务时，KnowledgeEngine 自动检索并向 prompt 注入相关知识；
7. 任务沉淀：失败产生 Pitfall，高效模式产生 Pattern，同样走 candidate 审核。

## C.3 Obsidian 集成

- 知识主存储保持 Markdown + frontmatter，兼容 Obsidian；
- `~/.dsh/obsidian/` 作为用户可见 Vault；
- 支持 `[[双链]]` 作为轻量知识关联；
- P0 提供“打开 Obsidian”入口，不做双向同步。

## C.4 知识图谱（Graphify）

- 引入 Graphify 作为知识图谱引擎，输入为项目目录/知识目录；
- 输出 graph.json / graph.html / Obsidian Vault；
- Weave 用 Cytoscape.js 展示图谱，支持 query / path / explain；
- Graphify 属于 P1，与 AnyDoc 不冲突。

## C.5 链接与浏览器采集（暂缓）

- P0 不做网页链接导入；
- 浏览器插件和浏览器自动化插件全部延后；
- 后续如需要，候选方案为 dsh-browser（本地 Playwright）或自研 Weave 浏览器插件；
- 当前不列入 Phase 0。

## C.6 与执行器模型的关系

- AnyDoc、Graphify、后续浏览器采集都作为“知识导入源/转换器”，不是执行器；
- 执行器仍保持四类：DSH 子代理 / Codex / Claude Code / ACP。
