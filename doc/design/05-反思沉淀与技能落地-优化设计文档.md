## 1. 审查结论（事实 + 证据）

### F1 ·【P0 · 断链】执行器知识沉淀（反思）只有"要求"，没有"实现"

- prompt 已要求执行器输出 `WEAVE_KNOWLEDGE_START/END` 标记
  （`delegation-service.ts:843-847`），测试也断言了模板存在
  （`delegation-service.test.ts:212-213`）。
- SDD 2.5.1/2.5.8 承诺"解析执行器输出中的 WEAVE_KNOWLEDGE 标记并沉淀 candidate"，
  但全仓库 `src/` 中**不存在任何解析与落库代码**（grep 仅命中 prompt 模板与文档）。
- 后果：SDD 4.3"角色学习闭环"最后一环（任务产出 → Pitfall/Pattern candidate → 再审核）
  实际断裂，执行器被要求输出标记但结果被静默丢弃。

### F2 ·【P0 · 断链】任务终态后无反思钩子；保温期机制未接线

- `WeaveScheduler.#afterTaskSettled`（`scheduler.ts:464`）只做：失败传播 SKIPPED →
  刷 DAG 状态 → 重泵。没有任何反思/学习入口。
- `FeedbackRouter.enterAwaitingFeedback` 注释"自动调用点：Orchestrator 委托完成路径"
  （`feedback-router.ts:98`），但生产路径从未调用（grep：仅测试调用）。
  COMPLETED 在调度器中直接终态，AWAITING_FEEDBACK/accept/revise 全链路不可达。
- 结论：**当前"任务执行后没有反思"**；反馈路由是有实现、无接线的半成品。

### F3 ·【P1】执行器执行中无法按需检索知识

- prompt 明示"P0 阶段无知识检索 CLI"（`delegation-service.ts:841`）。
- 注入是委托前一次性 `slim:true`（首段/≤200 字符）；MCP `dsh-mcp-knowledge`
  （`mcp/knowledge-mcp.ts`）只服务外部 ACP provider，DSH 内生执行器用不上。

### F4 ·【P1】知识"图谱"与注入脱节

- `web/knowledge-graph.ts` 仅为 [[双链]] UI 预览（不参与注入）；注入是
  freshness_first 权重平铺列表（`knowledge-engine.ts:50-58`）。
- 注入条目 `formatKnowledgeSection` 不输出知识 id（`delegation-service.ts:226-243`），
  执行器无法引用/回查某条知识。

### F5 ·【P1】沉淀协议与存储模型不匹配

- 模板 `{"type":"pitfall",...}` 无 layer/scope 字段；`KnowledgeType` 支持
  doc/skill/guide/pitfall/pattern/other（`knowledge-model.ts:20`），但 SDD 未定义
  执行器输出的 layer 路由规则，也未定义"不同执行器"的归属标记。

### F6 ·【P2】role 层知识只读不写

- 注入权重表给 role 层 0.8（同项目），但唯一写入路径 `ImportPipeline` 产 doc 类
  project 层卡片；role 层实际永远为空 → 角色维度注入形同虚设。

### F7 ·【P2】`scopeMatch` 用 `path.includes(project_id)` 子串匹配（`knowledge-mcp.ts:33-40`）

- `project_id=app` 会误命中 `application`；P0 可接受，需在文档标注。

### F8 ·【P2】`knowledge-mcp.ts` 输出总字符 2500 硬编码

- 与团队级 `knowledge_injection` 限额体系脱节。

## 3. 详细设计（本轮实施 R1–R5）

### 3.1 R1 解析协议（`src/plugins/weave/reflection.ts`）

```text
<执行器自由输出>
### WEAVE_KNOWLEDGE_START
{"type": "pitfall", "title": "...", "content": "...", "tags": ["..."], "layer": "project"}
### WEAVE_KNOWLEDGE_END
```

- `extractKnowledgeBlocks(text): ReflectionParseResult`
  - 标记行兼容 0..6 个 `#` 前缀与 CRLF；支持一段输出中多个块；
  - 块内必须是合法 JSON 对象，否则记入 `invalid` 计数并跳过（不抛错）；
  - 字段规整：`type` ∉ 枚举 → `'other'`；`tags` 非字符串数组 → `[]`；
    `layer` ∉ {project,role,instance,shared} → 视为未指定；
  - `title`/`content` 空或缺失 → 记入 `invalid`；
  - `ReflectionParseResult = { blocks: WeaveKnowledgeBlock[]; invalid: number }`。

### 3.2 R2 沉淀路由（`src/plugins/weave/reflection-service.ts`）

`ReflectionService.depositFromOutput(input)`，输入：
`{ taskId, executor, roleId, projectId, version, outputText }`。

路由规则（缺省 project 层，可由块内 `layer` 覆盖）：

| layer | 目录（KnowledgeStore.resolveAgentDir） | visibility |
| --- | --- | --- |
| project | `_agent/projects/{projectId}/{version}/` | project_only |
| role | `_agent/roles/{roleId}/` | role_only |
| instance | 需要 instanceId；缺失 → 降级 project 并记 error | instance_only |
| shared | `_agent/shared/` | global |

- frontmatter：`type` 透传（枚举外 → other）；`status` 由 `createCandidate`
  强制 `candidate`（AC-KNOW-003：不直接 active）；`confidence=0.1`、
  `freshness_score=1.0` 由 store 强制默认值。
- tags 追加溯源三元组：`executor:{executor}`、`role:{roleId}`、
  `source:weave-reflection` —— **"不同执行器"的沉淀以 executor tag + role 层路由区分**。
- filename：`reflect-{taskId}-{序号}.md`，双层消毒——服务侧预消毒（剔除 `\/:*?"<>|` 与控制字符）+
  store 侧 `createCandidate` 内 `safeKnowledgeFilename` 兜底（偏差 D2 核定后的最终表述）。
- 每条成功沉淀写审计事件 `knowledge.deposited`
  `{ knowledge_id, task_id, executor, layer }`（追加式审计，失败不阻断状态）。
- 返回 `{ deposited: Array<{id,title,layer,path}>, invalid, errors }`；
  单块失败不抛错（降级收集 errors），全部失败/无块 → 空 deposited。
- 审计事件类型注册：`AUDIT_EVENT_TYPES` 增加 `'knowledge.deposited'`，
  必填字段表同步（`audit/audit-log.ts`）。

### 3.3 R3 调度器钩子（`scheduler.ts`）

```ts
WeaveSchedulerOptions 新增（全部可选，缺省行为不变）：
onTaskSettledText?: (params: {
  task: TaskRecord; role: RoleConfig; team: TeamConfigLike;
  text: string; status: 'COMPLETED' | 'FAILED';
}) => Promise<number | void>   // 返回沉淀条数（>0 时调度器发通知）
```

- 触发点：COMPLETED 分支（`result: text` 已落库后）与 FAILED 分支
  （`result: text` 已落库后），各一次；
- 钩子异常：`log.warn` 记录后吞掉（反思失败不阻断调度主链路，与知识注入降级一致）；
- 返回 `n > 0` → `notify(run, "[weave] 反思沉淀 n 条候选知识（待审核）")`。

### 3.4 R4 装配（`index.ts`）

```ts
const reflection = new ReflectionService({ knowledge: deps.knowledgeStore!, audit: deps.auditLog! })
const scheduler = new WeaveScheduler({
  ...,
  onTaskSettledText: async ({ task, role, text, status }) => {
    const result = await reflection.depositFromOutput({
      taskId: task.id, executor: role.executor, roleId: role.id,
      projectId: task.project_id, version: task.version, outputText: text,
    })
    return result.deposited.length
  },
})
```

FAILED 也沉淀：失败现场（含 diagnostic 文本）正是 Pitfall 的主要来源
（SDD 4.3"任务失败/高效产出 WEAVE_KNOWLEDGE 标记"）。

### 6.1 P1-A 增量下发任务（任务池模式）

**目标语义**（对齐 `.agent-teams/weave-phase0-squad/team.json` 实证：`taskSeq: 42` +
`t1..t42` 跨批次递增追加）：同一 session 团队的任务编号跨批次递增；可向**在途 DAG**
追加任务与依赖；追加任务立即进入调度。

**API 语义**（`weave_plan_tasks` 参数扩展，向后兼容）：

- 新增可选 `append_to?: string`——目标 `dag_id`；缺省（现行为）新建 DAG，**不引入隐式
  自动 append**（显式优于猜测，避免误挂）；
- `append_to` 存在时校验：DAG 存在且属于当前 session 团队（`dags.team_id` 与会话绑定
  团队一致，否则 `invalid_argument`）；DAG 任一状态可追加（含 completed——复活场景），
  但追加到终态 DAG 时 `dags.status` 置回 `created` 并通知"计划已追加 N 个任务复活"。

**编号规则（DAG 域全局递增，对齐任务池 taskSeq）**：

- 新任务缺省 refId 不再每批从 `T1` 重来，改为 `T${既有任务数 + i}`（DAG 域单调递增，
  跨批次不冲突不重置）；持久化 taskId 仍 `${dagId}-${refId}`，天然全局唯一；
- 显式 `id` 仍允许（队长期望固定语义时），但须与 DAG 域既有 refId 不撞（查库校验，
  撞则 `invalid_argument: 任务 id 已存在`）；
- `depends_on` 解析域从"批内闭包"扩展为"批内新 id ∪ 目标 DAG 既有任务 refId"：
  允许新任务依赖既有任务、也允许既有 WAITING/BLOCKED 任务追加对新任务的依赖
  （后者本期不做——只支持新任务引用既有，避免改写既有行；在设计中登记为边界）。

**与在途调度器的交互（新增任务入泵）**：

- 追加任务落库（无依赖 → WAITING，有依赖 → BLOCKED）+ edges 插入后，调用既有
  `scheduler.start({ dagId, sessionId, parentAgent })`——`start` 已是幂等重入
  （`scheduler.ts:126-149`：run 上下文存在则刷新通知面后 `#enqueue`），`#pump`
  拾取新增 WAITING 任务即完成入泵，**调度器零改动**（T14 仅验证+测试）；
- 复活场景（终态 DAG 追加）：run 上下文已随 `settledNotified` 收敛，`start` 会重建
  run 上下文（`#runs.has` 为 false 分支）——需验证该路径 + DAG 状态刷新链；
- 环检测：批内节点 + 既有 edges 联合 `assertAcyclic`（复用现有函数，入参并集）。

**返回结构**：`{ dag_id, tasks: [仅本次新增], appended: true|false, existing_referenced?: [被引用的既有 refId] }`——新建路径返回不变（`appended: false`）。

**不做**（边界登记）：既有任务追加依赖、跨 DAG 引用、任务删除/回收——另轮。

### 6.2 P1-B 执行实时输出回灌会话

**现状链**：`delegation-service.ts` 已有五类事件（status/output/reasoning/tool_call/
tool_result）+ `onExecutorEvent` 回调出口 + 200 条环形缓冲（RPC 轮询用）；生产装配
（`index.ts`）**未注入回调**，事件止步缓冲；scheduler 仅离散节点 notifySession。

**设计**：新增 `session-stream.ts`——纯逻辑节流器 + 装配工厂，事件流经
`delegation → adapter → notifySession` 直达会话，**不经 scheduler**（零改动）。

```ts
// session-stream.ts（新文件）
export interface StreamOptions {
  enabled?: boolean              // 默认 true
  minIntervalMs?: number         // 默认 5000：同 (sessionId, taskId) 滑窗最小间隔
  maxChars?: number              // 默认 200：单条截断（excerptOf 风格）
  events?: ExecutorRunEventType[]  // 默认 ['output', 'status']——reasoning/tool_* 噪声大不回灌
}
export class SessionStreamThrottle { /* 纯逻辑：窗口/合并/终态 flush，可注入时钟 */ }
export function createExecutorEventNotifier(  // 装配工厂（index.ts 使用）
  opts: StreamOptions & { notify: (sessionId: string, text: string) => void; now?: () => number },
): (event: ExecutorRunEvent) => void
```

**噪声控制四件套**：①类型过滤（默认仅 output/status）；②滑动窗口节流（同任务 5s
一条，窗口内事件进 pending 缓冲）；③窗口到期合并发送（pending 文本拼接后仍截断
200 字符，避免碎片刷屏）；④任务终态 flush（`status: completed|error` 事件到达时
立即清空该任务 pending 补发尾包，防止最后一段丢失）。适配器整体 try-catch 吞错
（与 `#emitExecutorEvent` 同 philosophy：观察者不得影响委托主链路）。

**sessionId 来源**：`ExecutorRunEvent.sessionId` 当前可选且生产常缺。最小扩展：
`SchedulerDelegationContext` 增加 `sessionId` 字段（scheduler 的 run 上下文里有），
`executeTask` 发事件时带上——一处小接口扩展，避免每事件查库映射。

**开关与配置**：接入 `loadWeaveSettingsOverrides`（settings-store.ts 已有覆盖机制），
键 `execution_stream`（结构同 StreamOptions）；默认开启（5s 窗口 + 200 字符下，
最坏 1 任务 12 条/分钟，噪声可控）；用户可 `execution_stream.enabled: false` 全关。

**不做**：Web 面板实时流（RPC 轮询缓冲已覆盖）、按事件类型的分级订阅 UI——另轮。

### 6.3 P1-C DAG 依赖图画布自适应

> **实现状态修订（2026-08-28）**：本节视口缩放方案已退役——当前实现为**固定节点
> （92×30）+ 紧凑布局 `compactDagLayout`**，画布=内容精确尺寸放入滚动容器（横向溢出
> 走滚动，不做视口适配/铺满）；`fitDagLayout` 已 `@deprecated`，仅为兼容保留导出，
> 内部不再调用。下文保留作设计轨迹。

**现状**：client（`src/client/index.ts:2563-2566`）CELL 100×32 / GAP 30/8 写死，
画布宽=层数×130、高=行数×40，容器 `.weave-dag-wrap` overflow:auto；宿主面板
`dag/dag-panel.tsx:9-12` CELL 200×64 / GAP 48/24 同算法同病。界面大图小：
固定像素单元在小视口/大 DAG 下要么留白要么长距离滚动。

**方案选型**：布局参数化 + 容器测量（**选定**）vs SVG viewBox 整体缩放（否决）。

- viewBox 方案否决理由：现有节点是 DOM div（hover/selected/点击详情交互 + React 渲染），
  改 SVG 节点需重写全部交互与 20 个 client-bundle 用例锚定的 DOM 结构
  （`data-testid="dag-panel"/"dag-edges"/dag-node-*`），改动面与回归风险不成比例；
- 参数化方案：保留 DOM 节点 + SVG 边结构，仅把尺寸常量变为布局函数输出；
  `data-testid` 与 DOM 结构零变化 → 20/20 用例天然保持。

**布局函数**（两处共享同一数学，双实现）：

```ts
// dag-panel.tsx 导出（client 不能 import——bundle 禁 import 约束，手工同构移植）
export interface DagFitLayout { cellW: number; cellH: number; levelGap: number; rowGap: number; overflow: boolean }
export function fitDagLayout(
  viewport: { w: number; h: number }, maxLevel: number, maxRows: number,
  base = { cellW: 100, cellH: 32, levelGap: 30, rowGap: 8 },   // dag-panel 传 200/64/48/24 基准
  floor = { cellW: 56, cellH: 18, levelGap: 14, rowGap: 4 },
): DagFitLayout
```

逻辑：按 base 算固有 width/height → `scale = min(1, vw/width, vh/height)` → 四值
等比乘 scale → 低于 floor 任一值则钳到 floor 并 `overflow: true`（回落现滚动行为）。
节点字号随 `cellH` 联动（`fontSize = max(8, round(10 × cellH/32))px`）。

**容器测量**：ResizeObserver（浏览器全局 API，**无需 import**，符合 client bundle
约束）+ `useState` 存 viewport；`weave-dag-wrap` 高度改为 `min-height: fit 高`，
fit 模式下不滚动（overflow 隐藏），`overflow: true` 时恢复 `overflow:auto`。

**一致性护栏**：`dag-panel.test.tsx` 新增 fitDagLayout 纯函数用例（含 floor 钳制、
scale=1 上限、退化单节点）；client 侧 20 用例不改动语义，可加 1 例"小视口下
dag-panel 高度随 viewport 收缩"（可选）。双实现漂移风险由"用例锚定 base/floor
常量一致"缓解（client 常量与 dag-panel 导出 base 对齐写死在两侧用例）。

**不做**：力导向重排、节点折叠分组、缩放手势——超范围。

### 6.5 P1-G 调度作用域缺口：跨任务组饿死 + 已结束组治理失效（2026-08-28 落案）

**实证（本轮两处，队长取证 + 架构师复核）**：

- **G-① 跨任务组饿死**：developer-2/架构师空闲，但 adhoc-12 的 WAITING 任务始终不执行。
  根因是**作用域不对称**：角色互斥键 `activeRolePrefix(sessionId, roleId)` 遍历
  `#activeByRole` 是**会话全局**（跨 DAG 共占额度），而泵源事件是 **DAG 局部**——
  `#afterTaskSettled`（:570）与 `#executeReady` 的 finally（:426）都只
  `#enqueue(run.dagId)` 本组重泵。角色释放后其他 DAG 的 WAITING 任务无人拾取，
  直到该 DAG 自身再有事件——全静默时**永久饿死**。
- **G-② 已结束组治理失效**：adhoc-11/14 任务 retry 后永远 WAITING。run 上下文随
  DAG 收敛销毁（:359 `#runs.delete`），而 `onExternalRetry`（:203）以
  `runs.has(dagId)` 为前提**早退**；`onExternalCancel` 虽有 enqueue，但 `#pump`
  首行 `runs.get(dagId)` 缺 run 直接返回——**治理动作对已结束组双重失效**，
  队长被迫 cancel + 手动收尾。

**方案选型**：

- **G-① 角色释放全局重泵（选定）** vs 等待角色反向索引（否决：需维护
  roleId→dagIds 映射并在角色/DAG 生命周期各点同步，复杂度与收益不成比例）vs
  全局定时 ticker（否决：常驻定时器 + 延迟不可控，治标）。选定方案：`#executeReady`

  canTransition 三重闸），空泵成本仅一次 `loadDag` 读库；实现约 3 行。

  sessionId 从该 DAG 任务行取（`tasks.session_id` 同组一致）；parentAgent 未知置

## 7. 队长行为准则（用户定案，2026-08-28 落进插件本体）

队长模型是任务派发后的值守方。以下七条为**用户明确要求**的行为准则，已写进插件本体
（`host-wiring.ts` 导出 `CAPTAIN_DISCIPLINE` 常量，经 `weave_plan_tasks` 工具描述 +
返回汇总文本双通道提示队长模型；README §5「队长行为准则」同步）：

1. **在途值守**：有在途任务时队长不得结束会话回合——短周期轮询任务状态
   （`weave_get_status`），定时向用户通报进度，避免用户以为卡死；
2. **高频轮询与及时响应**：值守期间必须高频轮询（15 秒级）并及时响应——任务状态
   一变即向用户通报，用户消息优先处理，禁止长阻塞空等、禁止延迟汇报；
3. **完成即推进**：任务完成后主动读取交付物并推进下一步（下游任务或汇总答复），
   不等用户触发；
4. **失败走治理**：任务失败用 retry/cancel 等治理动作处理，不重开计划；任务派发后
   保持稳定，没有明确触发不变更任务组；
5. **增量追加（禁新建任务组）**：新需求一律经 `weave_plan_tasks` 的 `append_to`
   参数增量追加到当前任务组（§6.1 P1-A），编号域内自动递增；**非用户明确要求，
   禁止新建任务组**；
6. **看配置再派发（人员均衡）**：启动团队或团队变更时，先读团队人员配置
   （roles 全集/能力/stages），拆解任务按角色能力匹配；人员使用要均衡，禁止
   长期只用子集；无匹配角色的任务向用户说明而非硬塞；
7. **质量分层**：常规任务由开发自测与测试（tester）覆盖，QA 只做终审收口；重大
   任务块（跨模块/架构级/高风险）可让 QA 提前介入评审；**禁止每个任务都派 QA 审核**。

**支撑机制对照**：第 1/2 条依赖插件侧通知的完整性——调度器结算路径已有通知，旁路
（治理动作/反馈路由/恢复）静默问题由 **P1-D 任务状态变更通知单出口**（§6.4，T17–T20）
补齐；第 5 条依赖 **P1-A 追加语义**（§6.1，T13/T14，已实施）。准则文本单一来源为
`CAPTAIN_DISCIPLINE` 常量，README 与本文为同步镜像——后续修订先改常量与单测锚定。

## 8. 代码调用链图谱设计（code-map，2026-08-28 开发工程师-3 落案）

**用户需求**：快速查看代码调用链——"这个文件被谁依赖 / 它依赖谁 / 两个文件之间怎么走"，
服务改动影响面评估与新人导览。本期交付**模块级静态依赖图**的扫描→存储→查询→控制台视图
全链路；函数级调用图登记为二阶段边界（§8.2）。所有权：本节设计归图谱线（开发工程师-3），
实施任务 T59–T65（§8.6）按文件所有权派发。

### 8.1 选型①：静态扫描 = 自写轻量 import 解析（选定）vs madge / dependency-cruiser（否决）

**扫描面实证**：生产源码 51 个 ts/tsx（含测试约 90 个），模块形态单一——NodeNext 惯例
ESM，相对导入一律带 `.js` 后缀指向 `.ts` 源（`knowledge-engine.ts:1-3` 实样），bare
specifier 皆为 npm 包或宿主注入；根 tsconfig 虽为 `moduleResolution: bundler`，但只影响
tsc 编译策略，不影响源码 import 书写形态。运行时依赖仅 4 个（package.json dependencies），
团队对依赖保持克制。

| 方案 | 结论 | 理由 |
| --- | --- | --- |
| 自写轻量解析（**选定**） | ✅ | 语句形态仅三种（import / export-from / 动态 import），注释与字符串剥离后正则级解析即可覆盖；`.js`→`.ts/.tsx` 后缀探测是唯一解析规则；循环检测 DFS 约 20 行；零新依赖；纯函数直接进 vitest（madge 类 CLI 需 spawn 子进程，单测慢且输出随版本漂移） |
| madge（否决） | ❌ | CLI 工具定位：JSON 输出结构不稳定、嵌入库用需拖入 ts-graph 依赖树；本仓库无 paths alias（根 tsconfig 无 paths），其核心价值（alias 解析）用不上 |
| dependency-cruiser（否决） | ❌ | 依赖治理/规则校验能力强但重（读 tsconfig + rule 配置面大）；只为取"文件级依赖边"不成比例。其 forbidden-path 规则能力**登记为三阶段可选引入点**，不阻塞本期 |

**解析器规格**（`src/plugins/weave/code-map/code-scanner.ts`，纯函数无 IO，与
`web/knowledge-graph.ts` 的 `extractWikiLinks` 同级复杂度）：

```text
输入：仓库 src 下 ts/tsx 文件列表（调用方负责 glob 与读内容；排除 __tests__、*.test.ts(x)、dist）
抽取：import … from 'spec' ｜ export … from 'spec' ｜ import('spec')（记 importKind=dynamic）
解析：仅 spec 以 '.' 开头才建边；bare specifier 归 external（计数不建边）；
     '.js' 后缀 → '.ts'/'.tsx' 逐个探测（NodeNext 惯例）；探测失败计入 unresolved（不失败、不猜测）
输出：{ files, edges: [{from, to, symbols, importKind}], externals, unresolved }
```

防御性登记：本仓库现无路径 alias；未来若引入 alias，未解析 spec 落入 unresolved 而非
产出错边——失败可见优于静默错误。

### 8.2 图数据形态：模块级（本期必做）+ 函数级（可选二阶段）

**模块级（文件→文件带导出符号）**——节点/边模型与分层：

- 节点 = 源文件（相对 src/ 的 posix 路径，如 `plugins/weave/scheduler.ts`）；
  属性 `exports`（`export function/class/const/interface/type` 声明名正则抽取，尽力而为
  不保证全）、`loc`；
- 边 = `from 依赖者 → to 被依赖者`；属性 `symbols`（`import { a, b }` 命名符）、
  `importKind`（static/dynamic）；
- **分层 = 依赖深度，与 DAG `computeDagLevels` 完全同构**：入度 0（无人 import 的入口类
  文件，如 `client/index.ts`、插件 `index.ts`）为 level 0；`level(f) = 1 + max(level(importer))`。
  列从左到右 = 依赖深度递增（左=入口，右=底层工具），边恒自左向右——`compactDagLayout`
  的"列=层、行=同层内字典序"数学零改动移植（§8.4）；
- 循环依赖：DFS 定层遇环时环成员统一归 `max(成员层)`，结果计 `cycles: n`，UI 详情卡提示
  （检测告警，不做解环）。

**函数级（可选二阶段，本期不做，边界登记）**：需完整 TS AST 符号解析（re-export、解构、
默认导出、this/context 传递），成本高一个数量级。触发条件：模块级图上线后用户反馈粒度
不足再立项；届时优先用仓库已有 typescript compiler API（零新增依赖），不引 ts-morph。

### 8.3 存储与查询：独立 code-graph 缓存 + RPC（主干）⊕ 知识摘要条目（辅）

**主干（独立缓存 + code-graph RPC）**：

- 缓存失效：扫描时记录全量文件 mtime+size 指纹；指纹不匹配 → 响应带 `stale: true` 标记

| 每次 RPC 现扫（否决） | ❌ | 无缓存复用，多面板并发打开重复扫描；stale 可见性也丢失 |
